# 多帧上下文定位复测结论（2026-11-04）

本轮完成官方掩码核查、接口改造、两个失败案例试跑和五视频完整复测。**没有证据表明多帧上下文改善了当前系统；不据此追加训练或替换默认定位入口。** 编码实现、网络轨迹和v4 Kev权重全程固定，未启动训练，原问题与标准答案保留。

| 指标 | 原单帧定位 | 多帧上下文定位 |
|---|---:|---:|
| 原视频问答正确 | 3/5 | 4/5 |
| 带宽策略问答正确 | 4/5 | 3/5 |
| Kev问答正确 | 3/5 | 3/5 |
| Kev传输字节 | 2,099,495 | 2,236,828 |
| Kev相对同版本带宽策略省字节 | 8.71% | 5.49% |
| 播放卡顿 | 0秒 | 0秒 |

Kev新版本传输字节比旧实验增加6.54%。ROI定义变化会改变证据PSNR代理，因此不把旧/新reward差值直接当成改善。

碗案例的GT时间窗内6个非空掩码采样点，新旧定位都漏4个，暂定掩码像素覆盖率28.2%→29.0%，没有实质修复。官方掩码总帧数与发布视频有差异，这项覆盖率只用于诊断，不是官方J&F分数。毛巾两个检查点覆盖率已约99.9%，原视频问答却仍与green标注不一致，不能把它解释成编码损失。

已查实问答波动：完全相同的碗原视频请求，旧实验答pink，本轮答light blue；两个案例试跑时同一Kev接收视频答light blue，全量复测又答pink。两次请求的payload SHA完全相同。不能根据一次答对就归因于定位/编码进步，也不能根据一次答错就归因于Kev决策退化。

本轮保留两个被拦截的探索：18帧一起输出时出现多余帧ID和重复坐标；6帧批量输出时出现损坏JSON。都没有进入编码，没有自动重试。最终使用**每块最多6帧作为上下文、每次只返回一个目标帧的框**，复用原单帧响应验证。它使用块内后续帧，属于离线VOD预处理；跨块目标关联仍未实现。

整个改进过程共105次付费请求：82次成功定位、两例试跑6次QA、全量15次QA、被拦截探索2次。成功定位产生的候选在带宽/Kev间逐字节共享。60项测试通过，已验证完成命令再次执行只校验结果，不重复调用API。原ABR初始化与当前Kev检查点保持原哈希。

下一轮优先使用 [问题审校草案](evqa_grounding_review.md)：把右侧沥水架的碗明确写进新问题，另建任务版本；毛巾先人工复核光照、目标与参考颜色。新问题尚未调用API、未用于训练，也不改原EVQA评分。之后在清晰可回答的开发任务上验证定位，再冻结另一批未参与调试的视频作测试。当前五例已用于开发。
